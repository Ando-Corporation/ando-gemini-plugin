# Shared optional capabilities

Connected apps, miniapps, and automations are shared, non-messaging capabilities. Agent administration and personal notifications are also optional and retain their current eligibility checks. Capability selection is server-owned; this plugin cannot grant access or enable a tool with metadata or request fields.

Discover only capabilities needed for the user's request. If absent, state that this connection does not expose them. Do not imply installing the plugin enables every capability.

- **Connected apps:** verify the selected account with available connection reads; this is separate from Ando identity. Discover the account's tools and exact schemas before execution. Use each advertised typed `app_…` tool with its exact schema and selected `connection_id`. `search_app_tools` finds operations by need with `query`, and `get_app_tool_schemas` reads their exact contracts and effects; neither executes them. If your tools lack the typed tool, pass the returned `action` to the tool named in `run_with`, `run_app_read_action` or `run_app_write_action`. Older compact servers may expose `list_app_tools` and `run_app_tool`; use those only when actually offered. Never invent a typed tool name. Connect or reconnect only when requested and through the returned secure flow; never collect credentials in chat. Respect authorization for third-party writes.
- **Local connections:** a `list_connections` row whose `server_url` starts with `local-tool://` is a person's Claude Code or Codex on their own computer (provider `claude_code` or `codex`), given to you by its owner. Nothing dials that URL; it names a machine. It offers one action, starting a task.
  - Compact catalog: call `run_local_task` with its `connection_id`, the joined `conversation_id`, the `thread_root_message_id` of an existing root message (not a reply), a short `title`, the `task` (goal, what done looks like, and the context it needs; do not assume the session can read Ando), and optionally a `folder` the owner allowed (`get_app_tool_schemas` with `run_task` lists them; leave it out for the first).
  - Legacy (flat) catalog: the same action is `execute_tools` with that `connection_id` and the machine's `run_task`, with the same fields.
  - Either returns at once. The result arrives as an Ando notice in that thread and in your agent inbox; read it with `get_thread_replies` or `get_agent_inbox`, and never say the work is done before it does.
  - For work in one of the machine's projects, prefer it to a cloud sandbox: the session has the owner's checkout, setup and logins.
  - The owner's policy decides what a session may do. By default it may read and edit files in the allowed folders, run commands, push branches and use the network, and never merge, deploy or push to main unless the owner allows it; Ando refuses those commands inside the task, and the repository's branch protection is what holds main completely. While pushing is allowed the task holds the owner's GitHub sign-in, so pushes and pull requests are the owner's; other credential stores stay closed to it.
  - Runs happen only while the computer is awake and the desktop app is open, or while a server's connector is up. If the computer goes quiet, the task waits for it, and a run unheard from for 30 minutes ends with a failure notice in the thread and your inbox. You cannot move it to Ando's cloud (that control exists only for an Ando agent's task): start it again when the computer is back, or do the work where you run from the last pushed commit.
  - These tools are offered to agents only. A person connected as themselves cannot start a task from this chat, and a connection cannot be created or changed over MCP.
- **Miniapps:** human members and agents can publish and post command-backed instances when the capability and required grants are available. Publication requires `miniapps:write` and workspace write access; message posting retains conversation access and `messages:write` checks. Read the current command/instance contract, resource audience, and revision before interacting or editing. Read, update, publish, and install are distinct operations. Individual commands may have narrower eligibility requirements. Do not add an unsupported `revision` argument to a legacy command read.
- **Automations:** creating or editing an automation, scheduled message, or workspace script is a persistent action. Resolve schedule/timezone, destination, owner, and requested behavior first. Manage only within the authenticated principal's authority. Plugin installation does not create a listener or scheduled worker.
- **Agent administration:** current handlers may require a human principal and administrative grants. Shared classification does not make an agent eligible or let this plugin change the authenticated principal.
- **Personal notifications:** operate only on the permitted person's preferences. Current authentication restrictions still apply. Do not treat these as agent receiving settings or attempt them on an agent's behalf.

For custom miniapp records, read the instance with `get_miniapp_instance` when offered, then run one of its declared actions with `run_miniapp_action`. If the host advertises typed `mini_…` actions but not `run_miniapp_action`, invoke the matching advertised typed action with its exact schema and the instance identifiers. Never invent a typed action name. Preserve installation, generation and command identifiers on retries. Older servers may expose `read_miniapp` and `update_miniapp`. Do not substitute a different action when the exact one is unavailable.
